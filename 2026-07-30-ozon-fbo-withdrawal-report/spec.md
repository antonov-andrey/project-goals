# Ежедневный отчёт о товарах для вывоза с Ozon FBO

## Результат и проблема

Один отдельный ежедневный email должен перечислять доступные к вывозу единицы `Ozon FBO`, сгруппированные по текущему складу. Товар попадает в отчёт, если выполняется хотя бы одно условие:

- у текущего складского остатка подтверждено не менее 45 дней без продаж;
- один и тот же физический экземпляр прошёл не менее трёх циклов контакта с покупателем и возврата независимо от складов, через которые он перемещался.

Существующий `tool/ozon_fbo_return_cycle_report.py` считает возвраты по `offer_id` и `posting_number`. Такой подсчёт может сложить возвраты разных физических единиц одного артикула и поэтому не является допустимым источником автоматического решения о вывозе.

## Источники и границы

Сабмодуль `ozon_seller_api` владеет типизированными read-only операциями:

- `/v1/returns/list` — история возвратов, `exemplars[].id`, текущее место и статус возврата;
- `/v1/product/info/stocks-by-warehouse/fbo` — текущие `present` и `reserved` по SKU и складу FBO;
- `/v1/analytics/stocks` — число дней без продаж, а также `return_to_seller_stock_count` по SKU и складу;
- `/v1/warehouse/ozon/list` — канонические идентификаторы и названия складов Ozon.

Основной проект владеет выбором товаров, сопоставлением возвратного и товарного складов, безопасным содержимым письма и ежедневным расписанием. Отчёт только читает данные и отправляет email: он не создаёт заявку на вывоз, не меняет остатки и не изменяет карточки.

Письмо отправляется на `ManagerNotificationEmailTo`, включая нулевой отчёт. Полные идентификаторы экземпляров, КИЗ, barcode, GTIN, адреса складов, сырые ответы и тексты внешних исключений не попадают в письмо или журналы.

## Текущий остаток и количество к вывозу

Текущая единица доступна для новой заявки на вывоз только в строке складского остатка, где `present - reserved > 0` и `return_to_seller_stock_count = 0`. Расчёт выполняется отдельно для каждой тройки `shop_id`, `offer_id`, `warehouse_id`. Любое положительное количество в активной заявке исключает всю складскую строку; остаток того же артикула на другом складе проверяется независимо. `reserved` и `return_to_seller_stock_count` не вычитаются одновременно, потому что одна заявка может отражаться в обоих показателях.

Для причины отсутствия продаж к вывозу предлагается весь доступный остаток строки склада без активной заявки. Для причины повторных циклов предлагается только число сопоставленных проблемных экземпляров, ограниченное доступным остатком этого склада без активной заявки. Если обе причины относятся к одной строке, строка выводится один раз, количество к вывозу равно большему из двух рассчитанных количеств и не превышает доступный остаток. Если у уже выбранного кандидата отсутствует строка аналитики, цикл завершается ошибкой вместо отправки потенциально дублирующей рекомендации.

## Подтверждение отсутствия продаж

`Ozon` не отдаёт отдельный возраст текущей физической единицы и не отдаёт точное поле «дни без продаж на одном складе». Поле `days_without_sales_cluster` относится к кластеру, хотя строка аналитики содержит конкретный склад.

Чтобы не предлагать к вывозу недавно перемещённый или возвращённый товар, отчёт использует консервативное достаточное условие: строка текущего склада считается без продаж 45 дней только когда соответствующая строка `/v1/analytics/stocks` имеет `days_without_sales_cluster >= 45`. Отсутствие продаж во всём кластере гарантирует отсутствие продаж на конкретном складе, но может не включить склад, на котором товар залежался, если другой склад того же кластера недавно продал этот артикул. Отсутствующая строка аналитики не считается доказательством 45 дней.

В письме этот показатель называется «без продаж в кластере склада», чтобы не выдавать кластерную метрику за более точную складскую.

## Цикл конкретного экземпляра

Один цикл — одна уникальная пара `exemplars[].id` и `posting_number` из `/v1/returns/list`, в которой был подтверждён контакт покупателя с товаром:

- тип `FullReturn` или `PartialReturn`;
- причина начинается с `Покупатель отказался при вручении`;
- тип `ClientReturn`, то есть возврат после вручения.

Невыкуп без осмотра, ранняя отмена и технический возврат не считаются сигналом дефекта экземпляра. Повторные строки одного отправления дедуплицируются.

Проверка живых данных 30 июля 2026 года показала: `exemplars[].id` присутствовал во всех 507 строках возвратов FBO, одинаковый идентификатор повторялся в разных отправлениях и ни один идентификатор не встретился у двух разных `offer_id`. Поэтому основной счётчик строится по идентификатору конкретного экземпляра, а не по общему числу возвратов артикула. Возврат без идентификатора экземпляра в этот счётчик не входит.

Экземпляр с тремя и более циклами считается находящимся на текущем складе только по ограниченной эвристике:

1. его самая поздняя запись во всей истории, включая не входящие в счётчик технические записи, имеет `visual.status.sys_name=ReturnedToOzon`;
2. каноническое поле `place.name`, после удаления служебного суффикса возвратного склада `_ВОЗВРАТЫ` и нормализации регистра, совпадает с названием текущего FBO-склада;
3. на этом складе есть доступный текущий остаток того же `offer_id`.

Склады, через которые прошли предыдущие циклы, на счётчик не влияют. Если одному складу соответствуют несколько проблемных экземпляров, сначала учитываются экземпляры с наибольшим числом циклов, а их число ограничивается доступным текущим остатком. Идентификатор экземпляра используется только в памяти процесса и не выводится.

## Формат и расписание

Письмо содержит общий итог по артикулам и единицам, затем секции по текущим FBO-складам. Одна строка содержит:

- `offer_id`;
- количество к вывозу и доступный остаток;
- подтверждённые причины: число дней без продаж в кластере склада и/или количество проблемных экземпляров с их числом циклов.

Отчёт является отдельным worker в существующем сервисе `offer_bind`, чтобы не держать дополнительный постоянный Python-контейнер только ради одного ежедневного запуска. Он выполняется при первом проходе процесса, после успешной отправки планирует следующий запуск на 08:00 UTC и не меняет расписание создания карточек или существующего отчёта о непродающихся локальных товарах. Ошибка построения или отправки не переводит worker на следующее утро и остаётся итоговой ошибкой `BaseWorkerManager`.

## Проверка

Тесты `ozon_seller_api` должны доказать точные пути, payload, batch/cursor pagination, типизированный ответ и безопасный query-транспорт для трёх новых read-only операций, а тест возвратов — разбор идентификатора экземпляра, места и статуса из закреплённого официального ответа.

Тесты основного проекта должны покрыть:

- три возврата одного экземпляра и три возврата разных экземпляров одного артикула;
- дедупликацию повторной строки одного отправления;
- исключение невыкупа без осмотра и ранней отмены;
- накопление циклов одного экземпляра между разными складами;
- сопоставление склада из самой поздней записи экземпляра с текущим FBO-складом;
- исключение экземпляра не в статусе `ReturnedToOzon`, несовпадающего склада и нулевого свободного остатка;
- ограничение проблемных экземпляров доступным остатком;
- порог `days_without_sales_cluster` 44/45 и отсутствие аналитики;
- исключение пары `offer_id` и `warehouse_id` при положительном `return_to_seller_stock_count` без исключения другого склада;
- объединение двух причин без дублирования строки;
- безопасное письмо без идентификатора экземпляра и отправку нулевого отчёта;
- ежедневное планирование только после успешной отправки.

После публикации сабмодуля и основного проекта нужно пересобрать только `offer_bind`, дождаться первого завершённого отчёта, проверить одно письмо и сопоставить его строки с живыми остатками, аналитикой и возвратами Ozon. После этого новый процесс должен остаться без свежих `ERROR` или `CRITICAL`, а следующий запуск worker должен быть назначен на 08:00 UTC следующего дня.
